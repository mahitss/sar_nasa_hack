# Threat model

Status: design approved for later implementation. No authentication code, Supabase project, migration, or credential exists in this mission.

## Assets

- User identities and role assignments
- Incident membership
- Evidence records, decisions, and reports
- Catalogue identifiers and processing parameters
- Earthdata credentials on the worker host
- Satellite subsets on local disk and in Supabase Storage

## Trust boundaries

| Boundary | Rule |
| --- | --- |
| Browser | Holds the user session and the Supabase publishable key. Does not hold the service-role key, database password, or Earthdata password. |
| Go API | Verifies the JWT, then applies that identity to each pgx transaction. Owns authorization decisions. |
| Postgres | Enforces Row Level Security as a backstop. Does not trust a user id sent only as a query parameter. |
| Python worker | Accepts job ids from the database. Downloads only from an allowlisted Earthdata or ASF host, and only for granule ids stored on the job. |
| Git | Public repository. Contains no secrets and no large satellite files. |

## Authentication and row security

Supabase Auth issues the user JWT. Go is the verifier for API requests.

Verified identity in direct pgx transactions:

1. Verify the JWT (signature, expiry, issuer, audience) in Go before the transaction does any work.
2. Reject the request if verification fails. Do not fall back to an anonymous database role that can read incident rows.
3. On the same pgx transaction, set transaction-local JWT claims from the verified token and `SET LOCAL ROLE authenticated` before the first `SELECT` or `INSERT`.
4. Read and write through policies that join `incident_members` on `auth.uid()`.
5. Load privileges from `user_roles` in the database. Ignore role strings stored in user-editable metadata.
6. Reset is automatic at commit or rollback because the settings are transaction-local. Pooled connections must not use session-level `SET` for identity.

RLS is enabled on every application table. Policies to implement in the schema mission:

- `profiles`: a user reads and updates their own profile row. The profile has no privilege column.
- `user_roles`: no client insert, update, or delete.
- `incident_members`: members read their own membership. Admin writes go through a reviewed server path.
- Incident-owned tables (`incidents`, `acquisitions` linked to a case, `evidence_records`, `decisions`, `reports`, `processing_jobs`): access requires membership. Analysts draft measurements. Reviewers change review state. Viewers read.
- `audit_events`: insert by a security-definer trigger in the same transaction as the change. No client update or delete.

Looking up a row by UUID without the membership predicate is an insecure direct object reference, even when the identifier is hard to guess.

## Other abuses

| Threat | Control |
| --- | --- |
| Stolen service-role key | Key stays in server environment, never in `NEXT_PUBLIC_` and never in Git. `.env` is ignored. |
| SQL injection | sqlc generated queries. No concatenated SQL. |
| CSRF | Cookie-based Supabase SSR mutations use the framework's SameSite and origin behavior. State changes are not GET requests. A bearer token in an `Authorization` header is not sent cross-site by the browser. |
| XSS | React escaping remains on. Report text from the database is not rendered as HTML. |
| SSRF | The worker does not fetch a URL supplied by the user. Hosts are limited to Earthdata and ASF. |
| Path traversal and unsafe upload | Storage keys are generated by the server. User filenames are not path segments. Field-photo upload rules wait until a field mission exists. |
| Secret in a public commit | `.gitignore` excludes `.env` and `.env.*` except `.env.example`. The GitHub repo is public. |
| Large data leak via Git | Science extensions and `data/raw`, `data/processed`, and `data/derived` are ignored. |
| Audit tampering | Audit rows are append-only for authenticated roles. |

## Credentials this mission did not create

- No Supabase project
- No JWT secret
- No database password
- No Earthdata login
- No Bhoonidhi token

`.env.example` documents the names those later missions will use.
